The file tools now understand the `@name` shorthand the kernel writes into every agent's `TOOLS.md`, instead of treating it as an ordinary path segment.
An agent that followed its own generated instructions and called `file_list` with `@vault/notes` got `Failed to list directory '~/.librefang/workspaces/agents/<agent>/@vault/notes': No such file or directory` — a path it never asked for, naming a literal `@vault` directory under its private workspace.
The kernel had been advertising a syntax the runtime did not implement, so the model reasonably concluded the alias was unsupported and burned turns guessing other spellings; worse, an agent working around it could create a real directory called `@vault` that then silently shadowed the intended mount.
Expansion happens at the dispatch boundary, before the sandbox resolver and the read-only pre-checks run, so an alias grants nothing the absolute path would not: an unknown alias is rejected with the list of aliases the agent actually has, `..` in the remainder is refused, and a write through a read-only alias is denied exactly as a write to its absolute path is.
