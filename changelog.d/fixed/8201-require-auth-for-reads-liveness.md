Close the dashboard-reads allowlist when the first credential arrives through a config reload, instead of only on the next daemon restart.
The `require_auth_for_reads` default derives from whether any credential is configured, but that whole decision was snapshotted at boot, while `api_key` / `api_key_hash` reach the auth middleware live on `POST /api/config/reload` and on the config-file watcher tick.
An operator who booted with no credentials, then added an `api_key` and reloaded, kept `/api/status`, `/api/agents`, `/api/sessions`, `/api/config`, `/api/budget`, `/api/providers`, `/api/mcp/servers` and the rest of the read allowlist anonymously readable — and was told nothing, because the reload plan classifies `api_key` as effective immediately and reported `restart_required: false`.
The same boot snapshot applied to dashboard username/password credentials, which are classified hot with no restart flag as well, and which additionally decide whether the SPA shell at `/dashboard/*` stays publicly reachable and whether the fail-closed no-auth branch is armed; that flag is now a shared handle re-derived at every site that refreshes the master credential.
Only the configured flag pair (`require_auth_for_reads`, `external_auth_proxy`) is snapshotted now, because changing either genuinely requires a restart.
One term of the credential test still does not track a config-file reload and is now documented as such rather than implied to: the middleware's per-user API key table is replaced only by the `/api/users*` and device-pairing writes, so a hand-edited `[[users]]` block reaches the kernel's `AuthManager` on reload but not the middleware snapshot (#8201) (@houko)
