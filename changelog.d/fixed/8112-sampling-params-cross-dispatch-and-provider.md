Sampling preferences set through the dashboard (`top_p`, `frequency_penalty`, `presence_penalty`) reached the wire inconsistently depending on how a turn was dispatched: a per-model catalog override applied on the persistent-session path and silently vanished on the ephemeral (`/btw`) and streaming dispatch paths and on ephemeral worker spawns, none of which ran the resolution step the persistent path did.
OpenAI's reasoning models (o1, o3, o4-mini, gpt-5-mini) reject all three of those knobs exactly like they reject `temperature`, but only `temperature` had a proactive guard and a strip-and-retry arm, so setting any of the other three turned every turn into an unrecoverable 400 until an operator cleared the field by hand.
Ollama's native API only reads them nested under `options`, so the same three knobs reached the wire as an ignored top-level key instead of the sampling behaviour the dashboard's own hint promised.
The dashboard editor also clamped an out-of-range value to a number the operator never typed instead of reporting the conflict the way `PATCH /api/agents/{id}/model` does, and a negative `top_p` was silently dropped to "inherit" rather than clamped at all.
Fixed all four independently, and made `GET /api/templates` (list and detail) agree with `POST /api/agents` and the `agent_type_create` tool about which `agent-types/` document a name refers to when an embedder's `home_dir` differs from `LIBREFANG_HOME` (#8112) (@DaBlitzStein)
