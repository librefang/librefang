A workflow step that names an agent type now reports why starting that type was refused, instead of claiming the type does not exist.
The find-or-spawn resolver collapsed every outcome other than success into a bare `None`, and the engine renders `None` as "no template file and no registered agent with that name" — so a step whose run owner holds fewer capabilities than the type it names failed with a message that sent the operator looking through `agent-types/` for a file that was sitting right there.
The refusal itself is correct and unchanged: a step agent whose manifest asks for more than the run's owner holds is still rejected by the capability-inheritance gate, which is what stops a restricted agent from acquiring an unrestricted proxy through a workflow.
The resolver now returns a `StepAgentResolveError` that tells "nothing matches this reference" apart from "a template was found and the spawn was refused, for this reason", and the run error carries the reason verbatim.
Found while fixing it and fixed here too: the by-type test fixtures wrote to `workspaces/agents/<name>/agent.toml` under names the boot registry sync also installs into the canonical `agent-types/` directory, which is read first — so the fixtures were silently ignored and those tests ran against whatever the upstream registry shipped that day, over the network (#7858) (@DaBlitzStein)
