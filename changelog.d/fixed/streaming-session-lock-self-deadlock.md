A streaming turn on a session other than the agent's canonical one no longer wedges that session permanently the first time it crosses the compaction threshold.
The turn holds the per-session message mutex for its whole duration but never recorded that in the task-local held-lock registry, so the auto-compaction it runs before the agent loop looked the session up, saw nothing registered, and waited on the very mutex its own task was holding — a `tokio::sync::Mutex` is not reentrant and no other task could release it.
The turn then parked forever with the guard still held, so the client never saw a completion and every later operation on that session queued behind it, including a reset, which takes the agent lock first and so stalled every other session of that agent too; only a daemon restart cleared it.
Editor integrations were hit hardest: the ACP adapter derives a LibreFang session id from each editor session's own id and passes it to the kernel as an explicit override, which makes every Zed / VS Code / JetBrains conversation non-canonical by construction, so on default settings each of them hung as soon as its stored history passed thirty messages.
The dashboard reached the same state for any session pinned through `?session_id=`.
The streaming path now registers the session lock exactly as the non-streaming path already did, which also revives the cycle rejection for a re-entrant keyed `agent_send` issued by a tool during a streaming turn — previously dead code on that path, and a second way into the same hang.
A sibling trap found while tracing this one is closed too: `compact_agent_session_with_id` with no session id named took the per-agent lock and then took it again through the delegate's fallback arm, which no in-tree caller does today but which would have hung the first one that tried. (@houko)
