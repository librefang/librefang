`web_fetch` no longer loses every code block on a documentation page, no longer renders a blockquote as bold text, and no longer drops a `>` that a page wrote in prose.
All three came from the same shape: text resembling markup was destroyed by a rule meant for something else.
The conversion rules match an opening tag by prefix and run in sequence over the whole document, so a shorter tag name consumed a longer element before that element's own rule ever saw it — `<p` rewrote `<pre>` as a paragraph looking for a `</p>` that is not there, and `<b` made `<blockquote>` bold; matching now requires the character after the name to end it.
A preformatted block is lifted out before conversion and restored after it, since whitespace is the content there and every line was being trimmed, and the inline `<code>` rule was putting backticks inside the fence.
The fence is emitted for any `<pre>`, not only `<pre><code>`, because Python's documentation, the RFC series and compiler diagnostics all mark listings up without a `<code>` element, and a `class="language-…"` hint now reaches the fence.
Measured as `<pre>` elements in the source against fenced blocks in the output: Python docs 0 of 35 to 35, RFC 7231 0 of 101 to 100, the Rust book 0 of 15 to 15, the Rust Wikipedia article 0 of 29 to 29, SQLite's manual 0 of 3 to 3, and a GitHub README 1 of 12 to 12, with pages carrying no preformatted content unchanged (#7821) (@nevgenov)
