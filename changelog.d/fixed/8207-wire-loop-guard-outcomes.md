Wire the loop guard's outcome-aware detection into the agent loop, where it had never been connected.
`LoopGuard::record_outcome` and `get_poll_backoff` had no production callers: only the pre-execution `check()` ran, so the outcome counters stayed empty for the lifetime of every loop and `outcome_warn_threshold` / `outcome_block_threshold` / the poll backoff schedule were configuration that decided nothing.
A tool answering identically to identical parameters was therefore stopped only by the per-call counter, after four calls.
Results are now fed back to the guard after execution — in the sequential phase of both the serial and the parallel dispatch path, since the concurrent execution cores hold no mutable guard borrow — so such a call runs three times and is refused on the fourth instead of running four times and being refused on the fifth, and the model is told the results are not changing on the second repeat rather than only when the block lands.
Calls that never ran a tool body (fork-allowlist rejection, incognito `memory_store` drop, hook block) are not recorded, so the runtime's own refusals cannot accumulate as if the tool had answered.
A call that declares itself a poll — an explicit `"poll": true` parameter, or `shell_exec` running a recognised wait-loop command such as `docker ps` — keeps a budget relaxed by `poll_multiplier`, because an unchanged answer is what "not ready yet" looks like for a wait loop, and gets the backoff schedule's suggested delay appended to its result instead, which the model can act on without the loop stalling on a sleep.
That is still a shorter leash than before, and it is the one place a well-behaved agent will notice the change: a declared poll returning the same answer now runs nine times and is refused on the tenth, where the call counter alone let it run fourteen and refused the fifteenth.
The broader poll test `check` uses for its call counts — any parameters mentioning `status`, `poll` or `wait`, whatever the tool — is deliberately not used for the advisory or for the outcome budget, so an ordinary `task_list {"status": "pending"}` is never told to wait five seconds and is held to the strict three-result threshold rather than the relaxed nine (#8207) (@houko)
