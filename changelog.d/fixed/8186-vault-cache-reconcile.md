Storing or removing a secret through the kernel no longer erases every vault entry another writer added since the daemon started.
`CredentialVault` re-encrypts the whole file from one instance's in-memory map, and the daemon has more than one instance: the kernel caches one for its lifetime, `KernelOAuthProvider` opens a fresh one for each `mcp-oauth:*` entry, and `librefang vault set` runs in a separate process entirely.
Enrolling TOTP and then completing an MCP OAuth flow was enough to reach the bad state — the next kernel-side write dropped that server's client secret and tokens, sending it back to `NeedsAuth` and orphaning a dynamically registered client.
The kernel now re-reads `vault.enc` under the write guard before mutating it.
The same fix corrects a vault file created after the daemon booted, which the cached handle previously never noticed: reads reported a stored credential as missing for the rest of the process's life, writes failed permanently with `Vault init failed: Vault already exists. Delete it first to re-initialize.`, and deletes answered success without removing anything, so a credential an operator believed they had revoked resolved again after the next restart.
