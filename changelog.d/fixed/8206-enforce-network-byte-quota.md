`[resources] max_network_bytes_per_hour` in `agent.toml` now caps an agent's bandwidth instead of being a number that was written, read back and displayed but never consulted.
The field had a dashboard editor, a documented `0 = unlimited` convention, a 100 MB default and a full round-trip through the manifest APIs, yet no Rust code outside its own struct definition ever read it — the kernel kept no network byte counter at all, so there was nothing to compare a limit against.
Every other entry in the same `[resources]` table is genuinely enforced, which made this one worse than an absent feature: an operator who set a 1 MB cap on an untrusted agent was told by every surface that a cap was in force while the agent transferred gigabytes unmetered.
The scheduler now keeps a rolling-hour byte window per agent alongside its token and tool-call windows; the runtime reports what `web_fetch`, `web_fetch_to_file`, the WASM `net_fetch` host call and MCP tool responses actually read off the wire; and once the hour reaches the cap the agent's next egress tool is refused with the same quota-exceeded error the other limits raise.
The refusal is a soft denial, so a capped agent is told which quota stopped it and can keep doing local work rather than having its turn aborted.
Note the behaviour change on upgrade: the 100 MB default has always been what the manifest and the dashboard reported, and it now actually applies — an agent that legitimately moves more than 100 MB an hour needs an explicit larger value, or `0` for unlimited.
Host reachability is unaffected: that is `capabilities.network`, which was already enforced, and `docs/architecture/network-byte-quota.md` records exactly which paths the byte meter covers and which it does not (#8206) (@houko)
