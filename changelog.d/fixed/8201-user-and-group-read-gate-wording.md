Describe the enforced role gate on the `/api/users*` and `/api/groups*` reads accurately.
The middleware, the `users` and `groups` route modules and the TUI's group fetch all called it "the generic Admin-or-above read gate", but the predicate admits every authenticated role — a `role = "viewer"` per-user API key reads the account roster, per-user policy and group membership, deliberately, so the dashboard's user list and permission simulator work for whatever role opens them.
An operator planning a deployment against those comments would have assumed an Admin floor that was never implemented.
The wording now says which reads are open to any authenticated role, which are carved out (`GET /api/users/{name}/provider-keys` is Owner-only), and — rather than rounding the remainder off as harmless metadata — that `GET /api/users/{name}/policy` returns the unredacted per-user tool, category, memory and channel policy to any authenticated role, which is the same data the daemon gates at Admin on `GET /api/authz/effective/{user_id}`.
That inconsistency is described where both halves are implemented instead of being quietly resolved one way or the other, because raising the floor is a behaviour change for deployments whose dashboard opens the policy matrix under a non-Admin key.
The group-read unit test is renamed after the rule it exercises and pins the Viewer and User cases, so the docs and the predicate cannot drift apart again (#8201) (@houko)
