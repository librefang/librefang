Make the per-adapter dispatch cap actual backpressure instead of a cap on how many queued tasks are running at once.
The permit was acquired inside the spawned dispatch task, so the intake loop drained the adapter's stream at line rate and turned every inbound message into a detached, untracked task parked on the permit queue: under a burst that outran turn duration, later messages — including messages from users who were not flooding — were answered minutes late rather than shed, the backlog grew with the burst, and a shutdown or crash lost all of it silently because the recovery journal is only written once a dispatch starts.
The permit is now taken before the message is handed off, so a saturated adapter stops being read and its own bounded channel and overflow policy decide what happens to the excess; the debounced flush path takes its permit from the caller for the same reason, and both permit waits abort on the shutdown signal so a channel reload is not held for a full dispatch turn.
One consequence is new rather than pre-existing: the backpressure now propagates into a sidecar's inbound channel, where the default `overflow = "block"` parks the stdout reader once the buffer fills, and a single-threaded child that stops reading its stdin because its own stdout write is blocked will hit the ten-second stdin write timeout added alongside this.
`block` stays the default deliberately — for chat, slowing the producer beats dropping a user message, and that timeout makes the head-of-line case recoverable instead of a permanent wedge — while high-volume, loss-tolerant sidecars can still set `overflow = "drop_newest"` (#8198) (@houko)
