The agent-chat WebSocket no longer rejects the dashboard the daemon itself serves.
`validate_ws_origin` auto-allowed only loopback hosts on the listen port, so a browser that fetched the dashboard from `http://192.168.1.161:4545` sent that origin, matched no branch, and got a `403` — the product's primary use case failed out of the box on any deployment that is not loopback, and agent replies never reached the chat pane.
An Origin equal to the scheme, host and port the request itself arrived on is now always accepted: a browser sets `Origin` and `Host` independently and a page cannot forge `Origin`, so the two coincide exactly when this daemon served the page, while a cross-site attacker sends its own `Origin` next to our `Host` and stays rejected (#3731).
`cors_origin = ["*"]` now also works on the WebSocket, as it already did for CORS: the wildcard branch was gated on the `LIBREFANG_ALLOW_NO_AUTH` environment variable, an auth switch unrelated to origins, which left the documented wildcard permanently unreachable on this route.
A `"*"` entry no longer aborts the scan of the rest of the list with `Invalid extra origin URL: *`.
The rejection now names the request's own `Host`, the listen port and the effective allow list — reporting an empty list as `<empty>`, which is what a misplaced `allowed_origins` key produces — and the `403` carries a body naming the refused origin and the `cors_origin` knob instead of nothing at all (#7777) (@DaBlitzStein)
