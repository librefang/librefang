Stop rebuilding the `memories_fts` full-text index on UPDATEs that cannot change what it indexes.
The trigger installed with the index fired on every UPDATE of `memories`, including the per-fragment access-count bump every recall performs and the bulk confidence decay each consolidation sweep runs, so each affected row paid a full index delete plus re-insert that produced a byte-identical result.
That delete cannot use an index — `memory_id` is an unindexed fts5 column — so it scans the whole index per row, making any multi-row update quadratic in store size; on a large store the 24-hour decay sweep held SQLite's single write slot long enough for concurrent memory and session writes to fail with `database is locked`, and the access-count bumps those writes lost feed the decay engine's idea of which memories are stale.
A new migration re-creates the trigger with a `WHEN` guard on the two mirrored columns, so only a real content or agent change re-indexes (#8196) (@houko)
