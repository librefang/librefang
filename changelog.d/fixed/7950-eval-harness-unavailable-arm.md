The memory retrieval eval harness reported a wrong number with a confidence interval attached, which is worse than reporting nothing: a missing number sends you looking, while a confident one ends the investigation and gets pasted into an issue as evidence.
On a corpus copied from a database below migration v50 the `memories_fts` index does not exist, so the lexical arm returned nothing for every query, scored 0.0000, and the paired bootstrap — resampling differences that were just the leader's own scores — certified `fts5 | 0.0000 | +0.8709 [+0.7864, +0.9351] significant` for an arm that issued no query, while the fusion arm silently became the cosine arm under a second name because fusing a ranking with an empty list returns that ranking.
The index is now probed before any judging is spent and those arms are refused with the migration version they need, any arm that comes back empty for every counted query is withheld from scoring rather than certified, and the refusal travels with the table so a pasted result carries it.
Two calibration errors went with it: `verdict()` compared the noise floor against the interval bound *furthest* from zero, so `[+0.01, +0.20]` against a 0.040 floor was called a result when its own pessimistic end says the effect is unmeasurable, and the documented recipe for building a queries file produced queries that retrieve themselves — LibreFang stores every user turn verbatim in a `[Past exchange]` row, worth 0.1514 nDCG on the reporter's corpus, nearly four times the noise floor the harness declares for itself.
Queries files now take an optional `memory_id<TAB>text` column whose row is excluded from that query, the docs lead with a recipe that builds the file that way plus a temporal-split alternative, and the runtime guidance says what per-pair judging costs (~30x pooled, which is what makes `--judge-cache` load-bearing rather than convenient) and that grades are uncalibrated across documents.
The lexical arm also stopped killing the run outright on any real corpus: `memories_fts` indexes soft-deleted rows — a soft delete is an `UPDATE`, so the v50 trigger re-indexes the tombstone rather than dropping it — and the harness resolved those ids against a corpus loaded with `deleted = 0`, so a matching tombstone raised `KeyError` part-way through a judging pass that costs tens of minutes.
Two silent-wrong-number holes left over from that work are closed alongside it.
The `memory_id<TAB>text` heuristic reads a whitespace-free first field as an id list, so a real user message whose first word happened to be followed by a tab (`TODO<TAB>fix the retry budget`) silently lost that word and gained an exclusion id that matched nothing; every exclusion id is now checked against the corpus, and a run that cannot find one stops instead of scoring a query the harness truncated.
And a run in which every query was dropped raised `ValueError` out of the reporting layer as a traceback rather than reporting that it counted nothing, which is the one case the withholding logic already claimed the report handled. (#8077) (@houko)
