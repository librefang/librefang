A failed operation in the TUI now says what the daemon reported, everywhere the TUI talks to the daemon.
Twenty-one `spawn_*` helpers collapsed every non-success outcome into a single `_ =>` arm and printed a generic line of their own, discarding the reason the daemon puts in the response body — `YAML parse error at line 3` for a broken marketplace skill, `skill not found on registry` for a slug that no longer exists, `Re-issue with confirm=true to proceed` for a delete that needs confirming.
A generic failure line costs the operator a whole debugging round trip: it reads like the daemon fell over, so they go looking for a fault in their own installation while the daemon has already named a fault somewhere else, and the answer was sitting in the response the screen threw away.
That arm also erased the difference between *the daemon rejected this* and *the request never reached the daemon* — two problems with two different next steps, reported identically.
One shared `daemon_response` helper now sits in front of all of them.
It reads the reason out of both error envelopes in service — the nested `error.message` of `ApiErrorResponse`, which is what backups, sessions, memory KV, model overrides, provider keys and hands answer with, and the bare `error` string of the ad-hoc route tuples — falls back to the status line rather than inventing a cause when the body carries neither, and walks a transport failure's `source()` chain so `Connection refused` and `operation timed out` stop rendering as the same sentence.
Running a workflow was the last screen answering an unreachable daemon with a hardcoded English `Error: …` that no locale could translate; it now reports through the same workflow-run failure line every other outcome of that call already used (#8086) (@houko)
