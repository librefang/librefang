`apply_patch` now understands the `@name` form of a named workspace that `TOOLS.md` advertises to every agent.
Its paths live in the patch body (`*** Add File:`, `*** Update File:`, `*** Delete File:`, `*** Update File: old -> new`) rather than in a path argument, so the `ALIAS_PATH_KEYS` rewrite #8074 added at the dispatch boundary could not reach it: an agent that patched `@vault/note.md` was told `1 added` while the file landed in `<agent-workspace>/@vault/note.md`, and the vault copy never changed.
The parsed `PatchOp`s are expanded in the dispatch arm, before the read-only pre-check and before `apply_patch_ext`, so the denial of a read-only target stays a denial of the whole patch — expanding inside the tool left that pre-check reading raw header text, and the per-operation check downstream turned it into a partial apply with the writable half already written.
Rewriting the raw patch text was not an option: a `+*** Add File: x` line inside a hunk is a `new_line`, not an operation, and a `+@vault/y` line is meant to stay literal.
An unknown alias names the aliases the agent declared and points at the absolute-path form for a file whose own name starts with `@`; an alias target that names a directory — by spelling (`@name`, `@name/`, `@name/.`, `@name/sub/`) or because the path it resolves to already exists as one — is rejected with that diagnostic instead of surfacing `File exists` from the filesystem.
An `@name` rename now needs an absolute or `@name/...` destination: a relative one resolves against the agent workspace, so the file left the share and reappeared in the agent's own directory with a success response.
The same table also gains the two workspace-path arguments it was missing, `media_transcribe.out_path` and `speech_to_text.path`, and now supports a tool with more than one path: expanding only the input of a transcription while its destination stayed relative wrote the transcript into the agent workspace and reported success.
The transcript destination carries the same read-only prefix check as `file_write`, since the assistant may read its input from a read-only mount and the destination is opened with `truncate`.
An agent with no named workspaces keeps the old behavior — a leading `@` is a filename character (#8745) (@nevgenov)
