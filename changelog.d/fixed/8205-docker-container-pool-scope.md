Make `[docker]` `scope`, `reuse_cool_secs`, `idle_timeout_secs` and `max_age_secs` govern container lifetime instead of being settings that only round-trip through `GET /api/config`.
Every `docker_exec` call created a container and destroyed it again, so all three `scope` values behaved identically — including the documented `session` default, whose container did not survive to the session's next tool call — and the container pool that would have consumed the three timeouts was constructed only by unit tests.
An operator who set `scope = "agent"` to reuse one container across an agent's sessions saw the value echoed back unchanged while still paying full container startup on every single tool call.
Containers are now taken from and returned to a process-wide pool keyed on the configured scope, the container-shaping `[docker]` fields and the host workspace path, and a reaper applies `idle_timeout_secs` / `max_age_secs` every 60 seconds and destroys the whole pool on daemon shutdown.
`max_age_secs` counts from `docker run` rather than from the pool entry, so a container that is reused more often than its maximum age still retires on schedule instead of restarting its clock on every tool call.
`reuse_cool_secs` is a handover delay under `scope = "shared"` — the only scope that can hand one agent's container to another — and never makes an agent wait for the container it released itself.
Three consequences worth planning for before enabling the sandbox.
`shared` reuses the container whole, so whatever a previous call left in a writable path, in the `/tmp` tmpfs, or running as a process is inherited by the next agent; `reuse_cool_secs` delays that handover but sanitizes nothing, which makes `shared` appropriate only where the agents already trust each other.
A call that finds only a cooling or in-use container creates another one rather than waiting, and nothing but the reaper hands a container back to the host, so the idle container count per key settles at that key's peak concurrency and stays there for `idle_timeout_secs` — 24 hours by default, where it used to be zero because every container was destroyed per call.
Container names gained a per-instance suffix, since pooling means one agent can legitimately hold several containers at once and the previous name was deterministic per agent, which made two concurrent `docker_exec` calls collide on `docker run --name`; the suffix costs nine characters of headroom, so `container_prefix` is now capped at 45 characters instead of 54 (#8205) (@houko)
