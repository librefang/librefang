Report MCP transport failures from the tool-call path, so auto-reconnect can actually engage for a server that wedges after it has connected.
Nothing could move a connected server into an error state: `report_error` was only ever called from the connect and reconnect paths, so `should_reconnect` — which requires that state — was unreachable during normal operation, and the 60s health loop woke up every minute and did nothing.
The reported case ran for roughly two days across two different MCP servers and two agents, burning 19 tool calls to timeouts while `GET /api/mcp/health` reported both servers healthy, and only a daemon restart recovered them.
A failed tool call is now classified as transport-level (a timeout, a closed transport, a dead stdio pipe) or application-level (anything the server answered with a well-formed JSON-RPC error) and only the former reaches the health monitor, after three consecutive failures, so a slow tool or a bad argument never tears down a working server.
The reporting covers the per-agent workspace-scoped MCP pool as well as the daemon-global one — an agent with its own workspace dispatches through the former, so wiring only the latter would have left the reported configuration still unable to recover — and the synthetic `list_resources` / `read_resource` tools, which ride the same transport a wedge breaks (#8084) (@houko)
