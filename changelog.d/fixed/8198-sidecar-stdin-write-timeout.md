Bound the write that pushes a command into a sidecar adapter's stdin, which was unbounded and held the shared stdin mutex while it waited.
A sidecar that stayed alive but stopped draining its stdin filled the OS pipe buffer, and the write then blocked forever with the lock held, so every later send, threaded send, typing indicator and even the `shutdown` frame that adapter teardown writes queued behind a mutex that never unlocked — a channel reload, the natural recovery, hung on the same lock, leaving a daemon restart as the only way out.
The write now uses the same ten-second-bounded `write_line_timeout` helper the subprocess transport already exposes, and a timeout closes stdin, so later commands fail fast on the missing handle instead of queueing behind a lock that never unlocks; the child sees EOF, and the supervisor respawns the adapter only if the child exits on it (#8198) (@houko)
