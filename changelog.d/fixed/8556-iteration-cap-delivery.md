A turn that exhausts its iteration budget now delivers the best answer it has instead of returning nothing.
Previously, when the per-turn cap (`agent_max_iterations`, default 50) was reached, the loop returned `MaxIterationsExceeded`; the kernel's error arm only notified `alert_channels`, so the user saw silence indistinguishable from a hang. The non-streaming and streaming loops now build their response from the text accumulated across intermediate tool-use iterations — falling back to the same canned guard the normal end-turn path uses when there is none — and return `Ok` with a new `AgentLoopResult::hit_iteration_cap` flag. On the streaming path the best-so-far text is emitted through the existing stream pipe (WS/SSE/channel consumers receive it) when nothing was streamed already, and the terminal `Done` phase fires as it does on a normal turn. The assistant message is only appended when nothing was committed yet: interim tool-use prose is already in history, so the cap exit does not duplicate it. The kernel reads the flag to push a `max_iterations` operator notification, and the exit metric still buckets a capped turn as `max_iterations` rather than `completed`. The response is persisted (fork/incognito turns stay ephemeral). (#8556) (@DaBlitzStein)
