Deliver outbound channel messages to a channel instance whose name differs from its adapter type, which silently swallowed every reply on any fleet using a `<adapter>-<team>` naming convention.
The channel bridge keys its adapter registry by the `[[sidecar_channels]] name`, while every inbound turn is stamped with the adapter *type*, so an instance named `slack-hr` on type `slack` registered as `["slack-hr", "slack-hr:slack-hr"]` and was then addressed as `slack` + account `slack-hr` — a pair matching neither key.
The visible damage was worst after an approval: the tool ran, the agent composed its follow-up, and the reply was persisted to session history and never sent, so the human who had just tapped Approve saw nothing at all.
`channel_dm` and every auto-filled `channel_send` were dropped the same way, as were the interactive approval notification — which fell back to buttonless plain text, costing the approver the Approve / Reject buttons that are the notification's whole point — and every owner notification, whose registry pre-check rejected what the send itself would have delivered.
Resolution now falls back to matching the adapter's channel type, refusing to guess whenever two instances of one type could both answer, so a reply can still never cross into another tenant's chat (#8080) (@houko)
