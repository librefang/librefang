Refuse a passkey registration whose caller is not the principal the login ceremony authenticates as, instead of storing a credential nothing can ever use.
Registration filed the credential under the caller's own name while `authentication-options` looks up the resolved `dashboard_user`, so an operator who added a passkey while signed in with the master API key (attributed `root`) got `200 {"ok":true}` and "1 registered" from the dashboard, and then `400 no_passkeys` on every attempt to sign in with it — permanently, and with no way to clean the orphaned row up from a password session.
Registration now keys the ceremony and the stored row by the engine principal and answers `409 principal_mismatch` when the caller is somebody else.
The comparison is exact rather than trimmed, because the credential list and revoke endpoints look a row up by the caller's name verbatim: admitting a padded `[[users]]` name would file the credential under the trimmed principal and leave that caller staring at "0 registered" for a passkey it could not revoke — the same orphaned row, one indirection further in.
`passkey_enabled = true` with no `dashboard_user` configured now leaves passkey login disabled (`503`) rather than accepting enrollments for a login that has no identity to mint a session for, and the architecture doc records the one binding a reload cannot move: `dashboard_user` is hot-reloadable while the engine principal is fixed at boot, so a passkey-enabled daemon needs a restart after that field changes (#8201) (@houko)
