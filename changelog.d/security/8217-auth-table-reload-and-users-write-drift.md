Revoking a per-user API key by deleting its `[[users]]` block from `config.toml` and calling `POST /api/config/reload` now takes effect on the REST surface, instead of only on the WebSocket and terminal upgrades.
Those two re-derive their credential list from a fresh config snapshot on every connection, so an operator offboarding a user watched the revocation work there while every `/api/*` request kept accepting the deleted bearer at its old role — up to Admin — until the daemon was restarted.
The reload returned 200 and the field is documented as hot-reloadable, so nothing signalled that half the daemon had ignored it.
The 30 s config-file watcher and the dashboard credential-change endpoint had the same gap, and each one reaches a reload the others cannot see, so all three now republish the table.
The same shared table drifted the other way on write: any `/api/users` or `/api/groups` mutation rebuilt it from config alone, silently dropping the bearer of every paired mobile device and 401ing every phone until a restart, while `GET /api/pairing/devices` went on reporting them as paired.
Both faces had the same cause — nobody owned the rule that the live table equals config users plus paired devices — so the union is now spelled once, in `server::user_api_key_table`, and republished by `server::refresh_auth_tables` after every reload the kernel actually applied. (#8217) (@houko)
