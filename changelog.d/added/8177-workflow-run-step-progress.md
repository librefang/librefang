Expose the live step progress of a workflow run — `current_step_index` and `total_steps` on the run plus each step's resolved `variables` snapshot — through `GET /api/workflows/runs/:id` and `GET /api/workflows/:id/runs`, and persist `total_steps` in SQLite (schema v56) so a run recovered after a daemon restart reports real progress instead of "step X of 0".
Both executors report it, the sequential one per step and the DAG one per layer, so a workflow that declares dependencies — the shape whose progress is worth watching — is not the one that reports nothing.
A finished run never advertises a step it is no longer executing: the index is cleared on every transition out of Running, and the two endpoints read it through `WorkflowRun::live_step_index`, which answers `None` unless the run's state actually says it is running.
The variable snapshot is the bindings a step was dispatched with, not the ones its siblings went on to write, and each value is capped at the same 200 characters as the module's other debug traces — a run's persisted size would otherwise grow with the square of its own step count, every step carrying a full copy of every earlier step's output.
Note that `steps_completed` on the run list counts step *executions* while `total_steps` counts declared steps; a loop step contributes one execution per iteration, so the two are documented as not being a fraction. (#8177) (@DaBlitzStein)
