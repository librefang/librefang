New `librefang purge --agent <name>` CLI command removes every trace of an agent the operator already deleted: any roster entry left over (cascading to its sessions, memories and KV rows), rows a previous partial delete orphaned even when the roster entry is already gone, the agent's canonical UUID record in `agent_identities.toml`, cron jobs and event triggers keyed to its id, channel and conversation routing bindings keyed to its name, the workspace directory, and any agent-type template of the same name.
  Cron, trigger and routing residue matters because all three are recovered from the agent's *name* — the default `AgentId` is derived deterministically from it — so leaving them behind meant a new agent later spawned under the purged name silently inherited the old one's schedule, event wiring and `/agent` routing.
  The orphan scan walks the same shared table list the substrate's agent cascade deletes from, so residue in tables the cascade only learned about later — `pending_approvals` (v26), `goal_runs` (v42), `usage_events` — is found rather than reported as "no trace in this installation", which is the state older installations are actually in.
  Live agent ids are read straight from the `agents` table rather than through the hydrating roster loader, which drops a row whose manifest fails to deserialize or whose UUID is unparseable — exactly the damaged-row situation that leads an operator to run purge in the first place, and one where that live agent's rows would otherwise look like an orphan to cascade.
  Candidates are recovered even when the name currently has a live roster entry, so residue left by an *earlier* incarnation of the same name (recreated under a different id since) is removed instead of surviving under the report "nothing to purge".
  An id that has rows but cannot be attributed to any name — a child or ephemeral agent's `AgentId::new()`, never registered and already gone from the roster — is reported as present and deliberately left untouched, because purge cannot prove it belongs to the requested name and the safer error is to under-delete.
  The workspace directory is resolved the way spawn resolves it, through `workspaces_dir` and the agent's own `workspace` override, so a relocated workspace is purged instead of quietly surviving a run reported as successful; a hand agent's absolute override (`<workspaces>/hands/<hand>/<role>`) resolves against the whole workspaces root rather than failing validation against the `agents/` subtree alone.
  A directory is left standing when deleting it would destroy more than this agent: the workspaces root itself (`workspace = "."`), a directory another registered agent resolves to, one *containing* another agent's — `alpha` owning `shared` while a live `beta` owns `shared/team` — or one another agent declares in its `[workspaces]` table, which is the second way an agent gets a directory and resolves under the same root.
  An orphan has no manifest left to read, and the report says the location was not resolvable rather than claiming there was nothing there.
  Agent names are only required to be a single path component, so an agent named `my.bot` or `研究员` can be purged like any other.
  The command prompts for confirmation over the plan it just computed rather than a fixed warning (with `--yes` to skip — required when stdin is not a TTY), asks nothing when there is nothing to purge, and offers `--dry-run` to print the exact `PurgeReport` it would produce without changing anything.
  It refuses to run its destructive path while a daemon is answering for the installation, since a daemon holding the agent in memory re-persists a resurrected roster entry on its next save; `--force` is the override for an operator who has already stopped it by other means.
  A configuration that cannot be loaded aborts the command with a nonzero exit status before any database is opened, rather than falling back to the default installation's settings: for `--config /srv/instance-b/config.toml` that fallback would have moved the deletion to the default installation and purged its unrelated agent of the same name, which no warning can make safe.
  The target database is resolved through `[memory] sqlite_path` and `data_dir` exactly as the daemon resolves it, so a relocated layout is purged against its live database rather than a stale one freshly created at the default path.
  The plan the operator confirms names both the database and the home directory it is about to delete from, because removal categories say what kind of thing goes and only the paths say whose — and on a relocated installation those are two unrelated trees.
  A failed write to `agent_identities.toml` (a read-only home directory, say) is surfaced as a purge failure rather than reported as a successful removal, since the registry's own `purge()` only logs a warning on that failure and still returns success (#7986) (@DaBlitzStein)
