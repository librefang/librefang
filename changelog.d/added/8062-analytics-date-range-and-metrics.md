Date-range picker and the missing cost/SLO metrics on the Analytics page (#8062), because an operator running eight per-team deployments had given up on the built-in page and was maintaining a hand-written HTML dashboard against the same `/api/usage/*` endpoints — the endpoints have accepted `start_date` / `end_date` since #7891, but the page only ever asked for a fixed seven-day window, so "what did we spend last month, per model" was not a question the dashboard could answer.
  The window is now a first-class filter with quick presets (today / yesterday / 7d / 14d / 30d / this month / last month / all) plus explicit from/to inputs, and it applies to every metric on the page rather than only the trend chart; because the server filters on UTC calendar days, the picker resolves its presets in UTC and labels itself so, instead of silently reporting a window shifted by the viewer's offset.
  Newly surfaced: total tool calls, cost per call, first-event date paired with the configured `usage.retention_days` so a pruned history is distinguishable from a young deployment, a per-agent table carrying tool calls and the prompt/completion token split that labels hands rather than hiding their spend, the same input/output split on the model table, a range summary under the trend chart, and a CSV export named after the window it covers.
  `GET /api/usage/by-model/performance` gained a `p95_latency_ms` field — the one metric the issue asked for that the API genuinely did not have, and the number a latency SLO is actually written against, since the average hides the tail and the maximum is a single outlier.
  It is computed over the events that actually carry a measured latency, matching the percentile already reported per agent by `GET /api/agents/{id}/stats`: `usage_events.latency_ms` arrived as `NOT NULL DEFAULT 0`, so on a database upgraded across that migration every older row reads zero, and ranking those as though they were fast calls would have reported roughly the median of the real latencies as a 95th percentile (#8081) (@houko)
