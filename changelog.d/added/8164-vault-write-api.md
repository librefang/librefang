`GET /api/vault/keys`, `PUT /api/vault/keys/{key}` and `DELETE /api/vault/keys/{key}` let the dashboard and the TUI store the credentials the daemon resolves at runtime, closing the gap that made `GITHUB_TOKEN` reachable only from the CLI even though skill proposal and agent-type promotion already fall back to reading it from the vault.
  Writes take effect on the running daemon: they go through the kernel's cached vault handle, the same one `resolve_github_token` reads from, so a promotion attempted right after storing the token uses the new value instead of waiting for a restart.
  Values are never returned — the listing reports key names, whether the vault holds each one, and where the daemon would actually resolve it from, and there is no read-back endpoint at all — and only the keys on an explicit allowlist may be written, so the shared vault namespace the MCP OAuth flow also lives in cannot be overwritten or enumerated through this surface.
  That last piece matters on any host that already exports the credential in the daemon's environment: the environment is read first, so a listing that answered "is it in the vault" would report the key as unconfigured while promotion works, and report the same after a delete that revoked nothing.
  Every response now carries an effective `source` of `unset`, `vault` or `environment` alongside the vault-presence flag, so a surface can distinguish a credential that is genuinely missing from one that was stored but is inert.
  On a host with neither an OS keyring nor `LIBREFANG_VAULT_KEY` the write fails with a `503` naming the reason rather than silently downgrading to a cleartext `secrets.env` line.
  All three routes are Owner-only, including the listing.
  An Admin who could replace `GITHUB_TOKEN` would make skill proposal and agent-type promotion push under a token they chose and could break both by deleting it, which is the same class of action as the `/api/config/set` and per-user provider-key writes already withheld from Admin; the listing is gated for the reason the equally value-free `GET /api/users/{name}/provider-keys` is, since it enumerates the credentials an operator has configured.
